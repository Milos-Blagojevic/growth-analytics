# AGENTS.md

Python 3.11+ CLI tools: an Exa search client (`clients/exa_client.py`), a job-hunt pipeline built on it (`hunt.py`), a prospect pipeline for the owner's own product (`python -m prospects`: lead enrichment, value estimates and routing, kept in DuckDB) and a dashboard (`dashboard/`, run locally or on Railway) that shows the job-hunt pipeline's saved files, keeps the owner's statuses, notes and side projects, and starts `hunt.py` commands, from buttons, on a schedule or from an MCP client (its `/mcp` endpoint, which also serves its data and changes as tools), and keeps the Telegram chat bot (`hunt.py chat`, a Pydantic AI agent over the owner's Outlook and Gmail mail that also makes news digests on request) running on Railway. The root `README.md` covers setup, configuration, the command list and the files; each code folder has its own `README.md` that describes its part in detail. Read the folder's README before changing a feature.

## Layout

`hunt.py` stays at the root; the rest of the code is grouped by feature into folders, each with an empty `__init__.py` and a `README.md`. Modules import each other as `from <folder> import <module>` and call `<module>.<name>`, so tests can patch module attributes. A new module goes into the folder of its feature. A new folder must not be named like a data folder (`out`, `jobs`, `interviews`, `mail`: `.gitignore` ignores those names at any depth) or like a standard-library module.

## Commands

```bash
pip install -r requirements-dev.txt
python -m pytest
```

CI runs the same suite on Python 3.11 and 3.13 for every pull request and push to `main`. Keep code 3.11-compatible. The separate Verify workflow runs the `verify` skill on a pull request when it gets the `verify` label (see Skills).

Do not run these without asking: they spend money or send real messages.

- `python -m clients.exa_client`, `hunt.py discover`, `hunt.py run` (any mode): paid Exa calls; `run` without `--research-only` also pays for Claude and, when `TYPESAFE_API_KEY` is set, Jev. `run --fiber` (the dashboard's **With Fiber**, or `run --fiber` in `HUNT_SCHEDULE`) also starts one Exa agent run with Fiber per verified company ($0.09 to $0.40 each in the first trial).
- `hunt.py run` without `--dry-run`, `hunt.py send`: send to Telegram.
- `hunt.py interview-prep` and `hunt.py interview-review`: paid Claude calls that send the owner's CV or a whole interview transcript to Anthropic.
- `hunt.py mail` (any mode): reads the owner's mailbox and sends matching emails to Jev (when `TYPESAFE_API_KEY` is set) and Claude; without `--dry-run` it also sends to Telegram and updates `mail_state.json`. `hunt.py outlook-login` signs in to the owner's Microsoft account; `hunt.py gmail-login` to their Google account.
- `hunt.py chat`: polls the owner's Telegram bot (two pollers on one token interrupt each other) and answers with paid Claude calls that read the owner's mail and can create drafts in it; asked for news, it also makes paid Exa, Jev and Claude calls and updates `news_state.json`. With `LOGFIRE_TOKEN` set it also sends traces (no text) to the owner's Logfire project.
- `hunt.py news` (any mode): paid Exa, Jev and Claude calls; without `--dry-run` it sends to Telegram and updates `news_state.json`.
- `hunt.py monitor-sync`: creates, updates and deletes monitors on the owner's Exa account. A monitor it creates runs every 4 hours, billed $0.002 a run, until a later sync deletes it; never leave one behind after a trial. The dashboard's **New monitor** (Runs) adds a company to `monitors.csv` and starts it.
- `hunt.py monitor` (any mode): reads the monitors' runs (free), then paid Jev and Claude calls for each new posting, which send the owner's CV to Anthropic; without `--dry-run` it sends to Telegram and updates `monitor_state.json`.
- `python -m prospects run` (any mode): paid Exa calls, two searches per row of `prospects.csv`; without `--research-only` also a paid Claude call per prospect, which sends the product and pricing basis from `prospects.toml` to Anthropic. `python -m prospects discover`: one paid Exa agent run with Fiber, uncapped (about $0.75 in the first runs). `python -m prospects load` is free.
- `.claude/skills/verify/scripts/ci.py`, and the Verify workflow (adding the `verify` label to a pull request, or starting it from the Actions tab): a paid Claude session of up to `--max-requests` model requests.
- Deploying to Railway, or changing its service variables (a change redeploys and interrupts a running job).

`python -m dashboard` costs nothing by itself, but its Runs page, **Run selected**, **Re-run**, any `HUNT_SCHEDULE` entry and, with `MCP_TOKEN` set, the MCP endpoint's `start_job` start real `hunt.py` commands (paid, and possibly Telegram): always the `hunt.py` next to the `dashboard` package, whatever `--root` is. For a local smoke run, serve a temporary folder of sample files with `.claude/skills/verify/scripts/sandbox.py`, which runs a fake `hunt.py` for every job and `HUNT_SCHEDULE` entry (and, with `--chat-bot`, for the chat bot; with `--mcp-token`, for the MCP endpoint's jobs too); never use the owner's folder. With Docker, mount a fake over `/app/hunt.py`. Do not start jobs against the real `hunt.py` without asking. Tests pass a stub through `create_app(root, hunt_command=[...])`.

With `POSTHOG_PROJECT_TOKEN` and `POSTHOG_HOST` set (in `.env`, or in the environment of the dashboard or of a live `python -m evals` run), every `hunt.py` and `python -m prospects` command also reports to the owner's PostHog project, and so do the dashboard and a live eval: free and without text (see Conventions; the dashboard's opt-in Support widget is the one exception), but real data in the owner's project. Tests and the sandbox never do.

## Git workspaces

Agents work in separate linked folders (git worktrees), each on its own branch. The main checkout (the first entry of `git worktree list`) owns `main` and holds the owner's private files.

- Never check out `main` in a linked folder. `git checkout main` fails while `main` is checked out elsewhere; do not force it with `--ignore-other-worktrees`.
- To get the latest `main` in a linked folder: `git fetch origin && git switch --detach origin/main`. Start new work with `git switch -c <branch> origin/main`.
- After a PR merges, update `main` only in the main checkout, and only when asked: `git -C <main checkout> pull --ff-only`.

## Private files

`.env`, `profile.toml`, `cv.md`, `companies.csv`, `discovered.csv`, `watch_state.json` and `watch.log` (from the removed watch list), `out/`, `hunt.db`, `jobs/`, `interviews/`, `outlook_token.json`, `gmail_token.json`, `mail/`, `mail_state.json` and `news_state.json` hold the owner's secrets and personal data (interview transcripts also hold interviewers' words; `mail/` holds email subjects and senders; `outlook_token.json` and `gmail_token.json` give read access to the owner's mail and let drafts be created in it). They are git-ignored and kept out of the Docker image (`.dockerignore`); never commit them, and do not read `.env`, `outlook_token.json` or `gmail_token.json`. The ignore entries are globs (`hunt.db*`, `*_state.json*`, `outlook_token.json*`, `gmail_token.json*`) so that SQLite's WAL sidecars, the `.tmp` files the state writers replace and `news_state.json.lock` also stay out. On Railway the same files live on the `/data` volume and the keys are service variables. `hunt.db` holds the owner's statuses, notes and side projects, which exist nowhere else: never delete it, locally or on the volume. The dashboard keeps it in WAL mode, so `hunt.db-wal` and `hunt.db-shm` next to it hold the latest changes until a checkpoint: copy or back it up only while the dashboard is stopped, or the copy misses them. When a config or CSV format changes, update the matching template (`.env.example`, `profile.example.toml`, `cv.example.md`, `companies.example.csv`, `monitors.example.csv`) and the root README's Configure section.

`.logfire/` is where Logfire's own CLI saves a project's write token. The code never reads it (only `LOGFIRE_TOKEN`), but it is git-ignored and kept out of the Docker image the same way; do not read it.

`prospects.toml`, `prospects.csv`, `prospects_discovered.csv`, `prospect_runs/` and `prospects.duckdb` hold the owner's pricing, lead list and prospect research. They are git-ignored and kept out of the Docker image the same way (`prospects.duckdb*` is a glob so the scratch folder a rebuild works in stays out too). `prospects.duckdb` is derived and can be deleted; `prospect_runs/` and `prospects_discovered.csv` cannot be recreated without paying for the research again. Their templates are `prospects.example.toml` and `prospects.example.csv`.

`monitors.csv`, `monitor_state.json` and `monitor.log` hold which companies the owner has Exa watch and every posting judged for them, with its verdict and score. They are git-ignored and kept out of the Docker image the same way (`monitor_state.json*` is a glob, like the other state files'). `monitor_state.json` also holds the id that marks the monitors on the Exa account as this folder's: without the file `monitor-sync` starts over with new monitors, the old ones go on running, billed, until they are deleted on Exa's dashboard, and the postings already judged are forgotten. Never delete it while its monitors exist. `monitor-sync` deletes the monitor of every company `monitors.csv` does not list: it refuses to run while the file is missing or unreadable with monitors on Exa, or while `profile.toml` still has the old `[monitor].companies`.

## Conventions

- All Exa requests go through the `exa_client` module functions so retries and cost tracking apply. Never construct `Exa` elsewhere. Agent runs (`exa_client.agent_answer`) cost 10 to 100 times a search once a Connect partner is attached and have no cap: use one only for what the search API cannot do (a partner database), keep it behind a command or a profile setting the owner chooses, and never send a create again unless Exa refused it outright (429): after a timeout, a dropped connection or a 5xx the run may have started. A command that waits for agent runs in worker threads calls `exa_client.stop_agent_runs()` on `KeyboardInterrupt`, as `hunt.cmd_run` does: Ctrl-C does not reach the workers.
- Exa monitors (`pipeline/monitor.py`) run on Exa's schedule, which cannot be set to a time of day (a new monitor's first run comes at a minute Exa picks): `monitor-sync` only manages them, and the scheduled `hunt.py monitor` reads their runs through the API and decides when the owner hears about them. Keep it that way: no webhook route on the dashboard (the guard below admits none), and the webhook address Exa requires on every monitor stays subscribed to `monitor.deleted` only. A monitor create follows the agent-run rule (sent again only after a 429). Every monitor carries the id of the data folder that created it (`metadata.folder`, kept in `monitor_state.json`): `monitor.sync` takes over one of the folder's own that the state lost track of instead of creating a second one for the company, deletes one of its own that nothing lists, and never takes over, changes or deletes a monitor under another folder's id (a second data folder on the same Exa account owns it), only reports it. Runs are read from Exa's JSON, not through the SDK's run models, which refuse a run for one odd grounding row (`exa_client.monitor_runs`, `monitor_run_output`). What a run returns is web content, untrusted like email: it reaches Jev and Claude only as a posting's fields and text, through `monitor.findings`, which keeps titles on one line (they go into the Telegram message), and only postings that pass `research.own_postings` and the link check are judged. A posting is judged once, so nothing may write it off on weak evidence: an unreadable run and a posting that could not be scored are tried again (`monitor.MAX_TRIES` checks) before they are given up, and a link that cannot be checked is judged as unverified (`verify_roles(settle=False)`), not dropped.
- All TypeSafe requests go through `jev.ask` so retries and the usage tally apply. Jev is a screen in front of Claude: it only drops items it is confident about, anything uncertain or any Jev failure goes on to Claude, and a missing `TYPESAFE_API_KEY` means no screen. Keep thresholds as named constants and keep the scoring screen's hard rules in step with `scoring.SYSTEM_PROMPT`.
- Other HTTP goes through `requests` with an explicit timeout (15 s; Telegram uses 30 s). The Exa SDK passes its own timeout (600 s); `exa_client` replaces it with `TIMEOUT_SECONDS` on every request. Tests intercept `requests` only, so another HTTP library would bypass the mocks (the PostHog SDK and the OTLP log exporter send through `requests` too).
- Exa structured output (`search_structured`) allows nesting depth 2 and at most 10 properties in total, array item properties included. `research.RESEARCH_SCHEMA` and `enrich.money_schema` are at 10: adding a field means removing one.
- `scoring.SYSTEM_PROMPT` and the `Fit` model must agree. Verdict names also appear in `hunt.VERDICTS`, the digest code, `dashboard/queries.py` (`VERDICTS`), `dashboard/app.py` (`VERDICT_LABELS`) and the verdict colours in `dashboard/static/app.css`; change them together.
- A change to what `hunt.py` saves (result JSON, `_run.json`, `discovered.csv`, `mail/` files) must keep `dashboard/ingest.py` reading both the new and the already-saved format, since `out/` and `mail/` keep old files. `watch_state.json`, which the removed watch list wrote, is still read, so the watch-list postings tracked on Pipeline keep their titles.
- Email text is untrusted input. `mail_labels` gives Jev and Claude no tools and only reads probabilities and labels back, and email never changes a status by itself: `hunt.py mail` saves suggestions that the owner confirms on Pipeline (`email_updates.decide`). Keep both. `mail` asks for read-only access tokens (`outlook.READ_SCOPE`) even though the sign-in consents to `Mail.ReadWrite` for `chat`; never request `Mail.Send` or a Gmail scope beyond `gmail.compose`, and never add a tool that sends mail. The chat agent (`inbox/chat.py`) reads untrusted email and article titles with tools: its mail tools only read and create drafts, `news_digest` only runs the `pipeline/news.py` digest (the article excerpts go to Jev and Claude without tools, as in `hunt.py news`; each digest costs money and its topics go to Exa, so one answer makes at most `chat.MAX_DIGESTS` and a digest takes at most `chat.MAX_TOPICS` named topics of `chat.TOPIC_CHARS` characters; each answer starts with `jev.reset()` (`News.begin`), because `jev` remembers an outage for the life of the process and the bot runs for weeks), the failures a tool expects go back to the model as text (anything else fails the answer, with its traceback in the log), every answer is capped at `chat.MAX_REQUESTS` model calls, and neither the log nor the agent's traces carry message, email or draft text (a news topic can reach the log only in the error text of a failed Exa search or Jev request).
- Traces go to Pydantic Logfire, which keeps model messages unscrubbed and treats request URLs as safe. The chat agent records them with `InstrumentationSettings(include_content=False)` set on the agent (`chat.build_agent`; `tests/test_chat.py` checks that no text gets through), and `hunt.py chat` configures Logfire only when `LOGFIRE_TOKEN` is set. Never turn content on, and never add `logfire.instrument_anthropic` (it records every prompt in full: the CV, emails, interview transcripts and pricing that Claude reads), `instrument_requests` (it records URLs: the Telegram bot token is part of every Telegram URL, and mail searches are Graph `$search` and Gmail `q` parameters) or `instrument_httpx` (the Anthropic SDK's transport; with `capture_all` it records the same prompts). A new command that should send traces needs the same review.
- PostHog is a third party like Logfire, and everything for it goes through `clients/posthog_client.py`: never construct `Posthog` or an OpenTelemetry exporter elsewhere, and never add the SDK's model wrappers (`posthog.ai.*`, which record prompts and answers) or its `PosthogASGIMiddleware` (which puts the address asked for, naming a company or an interview, and the client's IP and browser on every event). What may be sent is what the module's functions take: for something the owner did on the dashboard an event name with properties that are values from fixed sets, booleans or counts (a status, a job kind, a run's mode, whether a discover was given a focus, its limit; `capture`); for a page of the dashboard the browser loaded, its route as it is declared and the declared route of the dashboard page it was opened from (`/c/{domain}`; `pageview`, from `app._ReportPageviews`, which reads the second off the `Referer` header in `app._previous_route`), never an address asked for or its query; for a model call or a chat tool call the provider, model, token counts, seconds, trace and session (`generation`, `parse_anthropic`, `agent_turn`, `instrument_tool`); for a call of the MCP endpoint's tools the events of PostHog's MCP Analytics SDK (`instrument_mcp`, `posthog.mcp`: the tool's name and description, its declared argument names, seconds, whether it failed and the error's type, the client's name, version and user agent), with what holds text taken off each one (`posthog_client._without_mcp_text`: the arguments, the result, an agent's stated intent, a tool name an agent made up, the error's message) and without the SDK's `context`, `llm_model` and conversation-id arguments; records written for PostHog (`log`, `command`); the dashboard's unhandled exceptions by type, stack and the route as it is declared (`capture_exception`, `configure(exceptions=True)`). Every event leaves as the owner's: `_before_send` gives each one, the SDK's own exception captures included, the one fixed distinct id `posthog_client.OWNER` and `process_person_profile: false`, so PostHog can follow the owner's events without a person profile. Never another distinct id, an `identify`, person or group properties, or person processing turned on: the dashboard has one password and no accounts, so there is no one else to tell apart. Never a prompt, an answer, a tool's arguments or result, text from an email, the CV, a transcript or `prospects.toml`, a company, domain, URL, title, note, id or the path of a data file, never an exception's message (it quotes such things: `_without_messages` takes it off every event, with each frame's path on the machine), and never one of the programs' own loggers (they name companies, senders and subjects). `hunt.py`, `python -m prospects` and `python -m evals` say how a command ended in its `finished` record (exit code, an exception's type), not as an exception. PostHog stays optional and out of the way: off unless both settings are given, turned on only by the entry points (`hunt.main`, `prospects.__main__.main`, `dashboard.__main__.main`, and `evals.__main__.main` for a `--live` run only: its free check stays off the network), no function of the module raises or waits for the network, and what is still queued when a process exits gets a few seconds (`TIMEOUT`, `RETRIES`, `FLUSH_MILLIS`, on the AI events' lane too) and is then dropped. A new dashboard action, model call, agent tool, CLI command or job kind reports itself the same way: follow the `posthog` skill (see Skills).
- The dashboard's Support widget is the one exception to "never text", and only when the owner turns it on (`POSTHOG_SUPPORT_WIDGET=1`, with both PostHog settings; `dashboard/__main__.py` refuses it without them). The pages behind the login, never `/login` (public on Railway), then load posthog-js from the project's assets host so the owner can open tickets in PostHog Support, and what the owner types in it, the name and email its form asks for, the browser, posthog-js's random session id and the address of the page a new ticket or a ticket recovery was started on go to PostHog (the widget adds the last two to its own requests). Its settings come from `posthog_client.support_widget` and nowhere else: everything posthog-js would capture by itself stays off (page views, autocapture, heatmaps, web vitals, exceptions, session recordings, surveys, product tours, feature flags), `base.html` drops every event but the widget's own (`posthog_client.WIDGET_EVENTS`) and takes the properties that hold an address off them (`WIDGET_DENIED_PROPERTIES`), and they leave as `OWNER` without a person profile. Widen it to other events, pages or settings only with the owner's say.
- The dashboard does not import `hunt.py` or anything that loads `.env` or the paid clients; shared file-format code lives in `pipeline/runs.py`, `interview/interviews.py` and `inbox/mail.py`, and the MCP endpoint reads the prospect ranking through `prospects/warehouse.py` (never `prospects/__main__.py`, which imports `hunt.py`). Of `clients/` it imports only `posthog_client`, which loads nothing.
- `hunt.db` has two kinds of tables (see `dashboard/db.py`). Derived tables are rebuilt from files by `ingest.py`; bump `db.SCHEMA_VERSION` when changing them. User tables (`tracking`, `side_projects`, `jobs`, `mail_decisions`, `mail_applications`) are never dropped or cleared: change them only by appending a migration to `db.USER_MIGRATIONS`, and never edit an applied one.
- `hunt.main` holds `runs.lock()` for every command except the interactive `outlook-login` (which writes only `outlook_token.json` and refuses to start while the lock is held), `gmail-login` (writes only `gmail_token.json`, which nothing else rewrites) and `chat` (long-lived; it must not hold the lock or no other command could run while it does), so a shell, cron and the dashboard never run two commands at once. Call `cmd_*` functions directly only in tests. `chat` shares `news_state.json` with `news`: both write it only through `news.record`, which takes a file lock of its own (`news_state.json.lock`) and reads the file again under it, and the chat bot records a digest's articles only after its answer was sent (`Conversation.settle`), as `hunt.py news` does. `chat` reads `profile.toml` for the digest but must keep starting for the mail without one it can use (`News.off` holds the reason).
- Every dashboard request must pass the guard in `app.py`: an allowed `Host` (loopback, plus `RAILWAY_PUBLIC_DOMAIN` and the host of `DASHBOARD_URL`) and, when `DASHBOARD_PASSWORD` is set, the session cookie (only `/login` and `/static/` are public). Every non-GET request also needs a same-origin `Origin` and the `X-CSRF-Token` header that `base.html` makes htmx send. New actions should be htmx requests from a page extending `base.html`; do not exempt routes from the guard. The one route that passes it another way is the MCP endpoint (`mcp_server.PATH`, served only with `MCP_TOKEN`): an allowed `Host`, no `Origin` but the dashboard's own, `Authorization: Bearer <MCP_TOKEN>` in place of the cookie and the CSRF token (neither of which opens it, and the token opens nothing else), POST only. Give it no second route, and add a tool rather than a route for what an MCP client should do. A tool that changes something must not be annotated read-only (clients run those without asking), and a paid job starts only through `start_job` with the token of a `preview_job`. `python -m dashboard` refuses a non-loopback `--host` without a password, and an `MCP_TOKEN` shorter than `mcp_server.MIN_TOKEN_LENGTH`; keep it that way.
- Dashboard jobs run `hunt.py` as a subprocess (`jobs.Runner`), never in-process: `cmd_*` functions call `sys.exit` and the `exa_client` cost tally is per process. Scheduled commands go through the same `jobs.build` validation and `Runner.start` as the Runs page, so a new schedulable command needs both a `jobs.build` kind and a `schedule._form` mapping.
- The chat bot on Railway is `dashboard/bot.py`: with `CHAT_BOT=1` the dashboard runs `hunt.py chat` as a supervised child (restart with backoff, stop at shutdown, output in `jobs/chat.log`), not as a job: no lock, no `jobs` row, `Runner.busy()` unaffected.
- The dashboard reads its settings (`DASHBOARD_PASSWORD`, `HUNT_SCHEDULE`, `CHAT_BOT`, `RAILWAY_PUBLIC_DOMAIN`, `DASHBOARD_URL`, `PORT`, `POSTHOG_PROJECT_TOKEN`, `POSTHOG_HOST`, `POSTHOG_SUPPORT_WIDGET`, `MCP_TOKEN`) from the environment in `__main__.py` and passes them to `create_app` (the two PostHog ones to `posthog_client.configure`, and to `posthog_client.support_widget` with the widget on); it never loads `.env`.
- The scoring model rejects `temperature`; do not add it.
- One failing company must not abort a run: `hunt.process_company` never raises and returns errors in its result.
- An open role is a posting where the company posts its jobs itself (`research._posts_own_jobs`: its own site, a site registered under its name, a host in `ATS_DOMAINS`). A posting on any other site is a lead, saved in `third_party_roles`: never an open role, never `best_role_url` (`scoring.score_company` takes off a best-role link that is not one of the open roles), never worth a paid fetch. Add a host to `ATS_DOMAINS` only when the link check tells its open postings from its closed ones, and keep `scoring.SYSTEM_PROMPT`'s third-party rule in step with that guard. The link check reads posting pages from any site: keep `research._says_closed` one pass over the page, with no parser or pattern that rescans on malformed markup (`tests/test_research.py` times hostile pages).
- In `prospects/`, Claude copies figures and never prices or chooses between them. `assess.Assessment` holds only what the research states (null when it states nothing, or when a figure is implausible: `assess.MAX_USD`, `MAX_HEADCOUNT`), every revenue and pricing-basis figure when it states several, and its disqualifier is limited to the ones in `prospects.toml` (`assess.output_model`); which figure counts (`value.pick`), the value range, tier and route are fixed rules in `value.py` on `prospects.toml`, applied again at every warehouse rebuild. Keep model calls out of `value.py` and `warehouse.py`, and keep `assess.SYSTEM_PROMPT` and `Assessment` in step. Web pages are untrusted input like email: Claude gets no tools there.
- `prospect_runs/` is the record and `prospects.duckdb` is rebuilt from it by `warehouse.build`: a change to what `run` saves must keep the rebuild reading the files already saved, and a change to the tables needs no migration. The rebuild skips what it cannot read with a warning and never fails on one file. `run` saves each prospect as it finishes, so an interrupted run keeps what it paid for. `python -m prospects` does not take `runs.lock()`; it shares no file with `hunt.py`.
- Dependencies are pinned in `requirements.txt` (runtime) and `requirements-dev.txt` (tests). `.claude/skills/verify/scripts/ci.py` pins its own in its inline script metadata (run with `uv run`): `pydantic-ai-harness` needs a newer `pydantic-ai-slim` than `inbox/chat.py` runs on.

## Tests

- Tests need no keys and make no network calls. The autouse `http` fixture in `tests/conftest.py` fails any test that makes an unmocked request.
- Mock Exa at the HTTP level with the `exa` fixture (`tests/exa_mock.py`, Exa wire format), so the real SDK builds and parses requests. Do not patch `exa_client` functions. Agent runs are mocked the same way (`exa.on_agent(agent_run(...))`: the create answers "queued", the status check answers the run).
- The Monitors API is an in-memory fake behind the same fixture (`exa.monitors()`, a `MonitorsMock`: create, list, get, update, delete, runs), in the wire format the live API answered with; add a monitor's runs with `add_run(monitor_id, monitor_run(...))`.
- Mock Ashby, posting pages, Telegram, Microsoft sign-in and Graph through `responses`; mock TypeSafe with the `jev_api` fixture (`tests/jev_mock.py`, its wire format); use the `claude` fixture (`FakeClaude`) instead of the Anthropic client (`fake_claude` for output models other than `Fit`). Microsoft Graph and the Gmail API are mocked through `responses` too; the chat agent runs on a scripted pydantic-ai `FunctionModel` (`tests/test_chat.py::scripted`), never on a real model; browser sign-ins are driven by `tests/browser_login.py`, which plays the redirect against the loopback server with `urllib` (outside the `responses` mock).
- PostHog is off in tests: `_isolate` clears its settings and shuts the client down after each test. To test what is reported, ask for the `posthog_api` fixture (`tests/posthog_mock.py`: capture v1's `/i/v1/analytics/events` and `/i/v1/ai/events` endpoints and the OTLP logs endpoint in their wire formats) and read `posthog_api.events()` and `posthog_api.records()`; do not patch `posthog_client` functions. Such a test puts recognisable text through the code (a company, a subject, a prompt) and asserts that none of it was sent.
- New behavior gets a test in the matching `tests/test_<module>.py` (dashboard: `tests/test_dashboard_<module>.py`, with pipeline files built by `tests/dashboard_data.py` and requests made through FastAPI's `TestClient`; prospects: sample config, Exa replies and saved runs from `tests/prospect_data.py`, and `tests/test_prospects.py` for the CLI).

## Skills

Before reporting a feature or behavior change verified or ready to merge, have it checked by an agent that did not write it: the `verify` skill (`.claude/skills/verify/SKILL.md`). Checkpoint commits and clearly marked draft PRs may precede verification; neither permits merging, deploying or paid operations. Standalone docs-only and test-only tasks skip review, but test-only repairs to existing blockers still need independent closure.

- Start with one full review in a fresh subagent/session without the implementation history. Pass the intended behavior, acceptance criteria and exact source snapshot; in Claude Code use `context: fork`, elsewhere pass the skill body with intent in place of `$ARGUMENTS`.
- After BLOCK or FIX BEFORE MERGE, fix the blockers and request one focused independent follow-up, preferably from the original reviewer. Supply the full report, reviewed snapshot, repair diff and check evidence to any replacement. Check the fixes, original blockers and their regression risks, not another unrestricted audit.
- Allow at most those two automatic stages per task. Preserve attempts, including interruptions, across sessions, replacement reviewers and branches. If blockers or incomplete evidence remain after follow-up, or a broad rewrite needs another full review, pause with findings, attempted fixes and a recommendation; ask the owner before further review. A canceled/rate-limited attempt is INCOMPLETE, not a silent retry or a reset of the count.
- Retain stable finding IDs and evidence-backed open/resolved/withdrawn dispositions. S3 suggestions do not force fixes or another review. Missing meaningful regression coverage can block, but supporting tests passing on the base or preferred assertions do not.
- Bind each report/check to the reviewed source snapshot. After edits, rebases or upstream integration, assess what evidence remains valid and rerun affected checks; do not inherit approval silently. The implementer cannot approve their own repairs. Missing essential checks and interrupted reviews are INCOMPLETE, never SHIP.
- Keep the stage count, reports, snapshots, remaining blockers and cleanup needs in the handoff or draft PR. The stage limit is coordinating-agent policy, not a runtime lock. The owner can request `/verify <intent>` or a follow-up with the prior report and snapshot; additional stages need explicit approval.

The Verify workflow (`.github/workflows/verify.yml`) runs one opt-in full review, not an automatic repair loop. `.claude/skills/verify/scripts/ci.py` gives SKILL.md and the pull request intent to a Pydantic AI `Coder` agent on a frozen copy in Docker without network access. It passes only a complete full report matching the frozen `HEAD:tree` snapshot, with required evidence and no blocking findings or failed checks. BLOCK, FIX BEFORE MERGE and INCOMPLETE fail the check; a standalone focused report cannot approve CI. The copy never holds files that HEAD lacks and that the working tree's ignore rules or the base commit's root `.gitignore` ignore (`ci.stage`), so keep private files ignored in the root `.gitignore`. SKILL.md must keep working there: relative paths, `$ARGUMENTS`, and a step 7 report matching `ci.Report`, `Risk` and `Check` (change them together).

`posthog` (`.claude/skills/posthog/SKILL.md`) keeps PostHog in step with the code. Follow it, before `verify`, whenever a change adds, renames or removes something PostHog hears about: a dashboard action (a non-GET route), a model call (Claude, Jev, Exa structured search or agent run, another provider), a chat agent tool, a CLI command or a dashboard job kind. In Claude Code the model loads it by itself for such changes; elsewhere read the file first. It says what each of these has to report and through which function, what may never be sent, which test proves both, and what the owner has to change in PostHog itself (an insight or dashboard built on an event that was renamed or removed). `verify` fails a change that leaves one of them unreported or that sends text.

`visualize-changes` (`.claude/skills/visualize-changes/SKILL.md`) builds an HTML report of the branch's changes in the git-ignored `.change-reports/`: short descriptions, before/after behavior, diagrams, old and new dashboard pages side by side, and a map of where the change lands, without a diff. Run it only when the owner asks for it.
