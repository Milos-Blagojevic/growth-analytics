# Dashboard app

The web dashboard (`python -m dashboard`): results, your tracking, interviews and side projects, starting jobs, and the schedule and chat bot when it runs on Railway.

## Files

| File | Purpose |
|---|---|
| `__main__.py` | Entry point and environment settings |
| `app.py` | FastAPI app, request guard and what goes to PostHog (an event per action, unhandled errors) |
| `auth.py` | Password login |
| `schedule.py` | `HUNT_SCHEDULE` parsing and scheduler |
| `db.py` | SQLite schema and user migrations |
| `ingest.py` | File ingest and `companies.csv` appends |
| `queries.py` | Page queries |
| `tracking.py` | Statuses and notes |
| `email_updates.py` | Status suggestions from email updates, and applications added from them |
| `projects.py` | Side projects |
| `jobs.py` | Job runner and cost estimates |
| `monitors.py` | The Monitors block on Runs: the companies in `monitors.csv` and whether each has its monitor, **New monitor**, **Edit** and **Remove selected…** |
| `bot.py` | The chat-bot supervisor (`CHAT_BOT=1`) |
| `mcp_server.py` | The MCP endpoint at `/mcp` (`MCP_TOKEN`): the pages' reads, changes and jobs as tools for an AI client (see [MCP endpoint](#mcp-endpoint)) |
| `templates/` | Jinja templates |
| `static/` | CSS and a vendored copy of htmx 2.0.7 |

## Dashboard

```bash
python -m dashboard              # http://127.0.0.1:8000
python -m dashboard --port 8001
python -m dashboard --root ~/hunt-data   # data folder other than the current directory
```

Run it from the project directory, or point `--root` at the folder holding `profile.toml`, `companies.csv`, `out/` and the other data files (jobs then run `hunt.py` with that folder as working directory). By default it listens on `127.0.0.1` only and has no login, so every request must name a loopback host. Every change (status, notes, projects, starting a job) must carry a token from the page and come from the dashboard's own origin, so another website open in your browser cannot start a paid run. The origin is read from the `Origin` header, which browsers send with every such request; a request without it (a script) is refused, even with the token. If the dashboard restarts, open pages hold an old token: changes then show "This page is out of date… Reload it". The [MCP endpoint](#mcp-endpoint) is the one exception: it takes a token of its own instead.

With `DASHBOARD_PASSWORD` set (at least 12 characters), every page asks for that password first, and a session lasts 30 days on that browser; **Log out** ends it. Changing the password logs every browser out. After 10 wrong passwords in 15 minutes, logins are refused for everyone, you included, until the 15 minutes pass. Serving beyond this machine (`--host` other than loopback) refuses to start without a password. Besides loopback, the dashboard accepts the host names in `RAILWAY_PUBLIC_DOMAIN` and `DASHBOARD_URL`. The dashboard reads `DASHBOARD_PASSWORD`, `HUNT_SCHEDULE`, `DASHBOARD_URL`, `RAILWAY_PUBLIC_DOMAIN`, `PORT`, `POSTHOG_PROJECT_TOKEN`, `POSTHOG_HOST`, `POSTHOG_SUPPORT_WIDGET` and `MCP_TOKEN` from the shell environment only, never from `.env` (`export DASHBOARD_PASSWORD=…`, or `DASHBOARD_PASSWORD=… python -m dashboard`); the `hunt.py` jobs it starts load `.env` as usual.

Reading pages costs nothing. Only jobs you start on Runs, or with "Re-run" or "Run selected", the commands in `HUNT_SCHEDULE` and the jobs an AI client starts through the [MCP endpoint](#mcp-endpoint) call Exa, Claude or Telegram. Jobs you start ask for confirmation first.

- **Board** (`/`): the latest scored result per company, in tabs for apply, consider, stretch, check careers and skip, with search (company, role, location and your notes), a status filter (dismissed cards are hidden unless you choose All or Dismissed), a minimum score and sorting. Each card shows the score, best role, location assessment, whether the posting link was confirmed live, a "third-party listing" tag when the research saw a role only on a third-party site, and your status. A company whose latest run failed keeps its last scored result, and the board names the companies that failed in the most recent run. Click a card for the details: best role, your status and notes, next step, scope and gap notes, reasons and concerns, side-project ideas, the application kit when one was written (see below), score history across runs (with the 75 and 50 thresholds), open roles with link status, roles seen only on third-party sites (leads to look for on the company's careers page, see Third-party sites in [Run](../pipeline/README.md#run)), dropped dead links, research warnings (for example a failed ATS fallback search), company summary, evidence URLs, and a **Re-run** button that researches just that company. `/c/<domain>` opens the same details as a page.
- **Application kit**: a company whose latest scored result has a posting link gets a **Write application kit…** button in its details (**Rewrite application kit…** once it has one). The confirmation shows the command (`hunt.py apply-kit <domain>`), the cost (one Claude call, a few cents; about $0.001 from Exa when the posting text has to be fetched) and what is sent: your profile, CV, the posting and its application questions go to Claude, and the posting's application form is read from its job board. When the job is done the details show the kit: which posting it is for and when it was written, the CV points to lead with, a short note to the hiring team, each application question with a drafted answer, a "Before you send" list of what to fill in or verify, and the token counts. A kit written for another posting than the current best role says so. Nothing writes a kit by itself, and nothing is sent to the company: you copy the text into the form. See [Application kit](../pipeline/README.md#application-kit).
- **Your status and notes**: set a status (new, saved, applied, interviewing, offer, rejected, dismissed) and free-text notes in a company's details, or change a status on Pipeline. Notes save as you type. A role is tracked by its posting URL, so when a later run picks a different best role for a company, the card starts as new again. A company without a posting (check careers) is tracked by its domain, and an application added from an email update (see Pipeline) by that email. The first time an item reaches applied or later, the date is kept as "applied": the day you set the status, or the date of the confirmation email when you confirm the application from one.
- **Pipeline** (`/pipeline`): everything you marked saved, applied, interviewing, offer or rejected, in columns, with your notes and applied date. Change a status there to move the card. Above the columns, "From your email" lists the application confirmations, rejections and interview invites `hunt.py mail` found, each with the applications it matches and a button to set the status (**Mark applied**, **Mark rejected**, **Mark interviewing**). An update that matches nothing you track (an application you made outside the board) has **Add to pipeline** instead, which adds it as a card with that status (see [Email updates](../inbox/README.md#email-updates)). An application confirmed from its confirmation email keeps the email's date as its applied date, unless it had one already. With two or more confirmations waiting, **Add all N application confirmations** confirms them in one click: one that matches nothing you track is added, one that matches exactly one application is set on it, and one that matches several stays for you to pick.
- **Interviews** (`/interviews`): your interviews on a board by stage of preparation (needs prep, ready for the call, to review, reviewed), the watch-outs for your next interview, and progress across reviewed interviews. Each interview has its own page to open on your phone before and during the call. See [Interviews](../interview/README.md#interviews).
- **Projects** (`/projects`): side projects that build proof for your gaps, in idea, active, done and dropped columns. The scorer writes side-project ideas only for stretch roles (a role centred on one of your `[candidate].gaps`). Every idea from any saved run appears as a suggestion, newest run first, with the company, role, that run's score and verdict, and its age. Ideas from older runs stay even when a later run scores the company differently, because they are about your gap, not the company. **Add to ideas** turns one into a project, and **Dismiss** hides it. A handled idea is not suggested again, even if a later run repeats it with different case or spacing. **New project** adds your own, with a title, description, the gap it covers and a repository or write-up link. Deleting a project the scorer suggested hides it rather than letting it come back.
- **Leads** (`/leads`): companies from `discovered.csv`, marked new, queued (in `companies.csv`) or researched (with the latest score). Tick companies and press **Run selected…** to research and score just those (they do not need to be in `companies.csv`), or **Add to companies.csv** to append them to `companies.csv`, so every full run (scheduled ones too) covers them. Companies already listed are not added twice (domains are compared as `run` reads them, so `https://www.Acme.com/` and `acme.com` are the same company); removing one means editing `companies.csv`.
- **Runs** (`/runs`): start `hunt.py run` (dry run, run and notify, or research only, each optionally with Fiber) for every company in `companies.csv`, `discover` (focus, limit), `mail`, `followup` or `news` (each optionally dry run). **Follow-ups** (`followup`) sends the applications that have had no reply for 8 days to Telegram, each once, with whether its posting is still open; it is free (see [Follow-ups](../inbox/README.md#follow-ups)). Each opens a confirmation first. It shows the exact command, an estimated cost and side effects such as Telegram messages, file updates or what is sent to Claude; for a run you can switch the mode and **With Fiber** there, also for **Re-run** and **Run selected**. With Fiber, the run also asks Fiber's jobs database for each verified company's open roles (`run --fiber`, one paid Exa agent run per company; see Fiber as a role source in [Run](../pipeline/README.md#run)); it is off unless you tick it, whatever `profile.toml` says. Saved runs made with Fiber are marked "· Fiber" in the history. A `discover` focus may not start with `-`, so it cannot be read as a flag. Checking the monitors (`monitor`) and syncing them (`monitor-sync`) have no button: they run from `HUNT_SCHEDULE`, and **New monitor**, **Edit** and **Remove selected…** under Monitors sync. Resending a saved run's notification is `hunt.py send` on the command line.
  - **Monitors:** the companies in `monitors.csv` (see [Monitors](../pipeline/README.md#monitors)), each with how `monitor_state.json` says it is watched and since when: "job board at <host>" for a company that is read from its job board's public feed (free), "on Exa" for one with a monitor, and "not on Exa yet" until a sync settles it, or when the last one failed or could not start (its job log says why, and the next sync does it). The first 10, in the file's order, are listed; **Show all** lists the rest. **New monitor** asks for a company name (up to 100 characters) and domain, shows the command, the cost (about $0.12 a month for a company that needs a monitor, nothing for one read from its board) and the side effects, then adds the company to `monitors.csv` and starts `monitor-sync`, which creates its monitor or reads its board, so the next scheduled `monitor` reads what is new. Nothing is added while another command runs, for a domain listed already, for a name or domain that cannot name a monitor (the domain must be a bare host name such as `acme.com`), for a `monitors.csv` the sync could not read, or while `monitors.csv` is missing and `monitor_state.json` lists monitors: a list of the new company alone would make the sync delete the others. The block names the last two problems. Domains are compared as `run` reads them. **Edit** on a company opens the same form with its name and domain: **Save and sync** changes its row in `monitors.csv` and starts `monitor-sync`, which updates its monitor's search for a new name; for a new domain (a typo fixed) it deletes the old domain's monitor and creates one for the new domain, and the postings judged for the old domain are forgotten. Tick companies and press **Remove selected…**: the dialog names them and says what the sync does, and **Remove and sync** deletes their rows and starts `monitor-sync`, which deletes their monitors (their billing stops, and the postings judged for them are forgotten). Edit and Remove refuse what New refuses, a company `monitors.csv` no longer lists, a domain another row lists and an edit that changes nothing, and change nothing while another command runs. They leave the rest of `monitors.csv` as it is written (comments, blank lines, extra columns), and write it whole at once, so a crash never leaves half a list for the next sync to delete monitors by.
  - **Schedule:** the commands in `HUNT_SCHEDULE` (see [Deploy to Railway](#deploy-to-railway)) with their next time and the job each last started, or why it could not start.
  - **Chat bot:** with `CHAT_BOT=1`, whether `hunt.py chat` is running (since when, starts, the tail of `jobs/chat.log`, refreshed every 5 seconds); otherwise a note on how to turn it on (see [Chat with your mail](../inbox/README.md#chat-with-your-mail)).
  - **Estimates:** Exa is the average cost per company of saved runs that recorded it (`_run.json`), runs with Fiber and runs without averaged apart; until a run with Fiber is saved, a run with Fiber adds $0.09 to $0.40 a company to the estimate without it. Claude is the figure in [Parked ideas](../docs/parked-ideas.md) of $0.27 per 19 companies, an upper bound now that the Jev screen skips Claude for some companies. Jev is a fraction of a cent. Discover is the figure in [Run](../pipeline/README.md#run) of $0.15–0.20.
  - **Job pages:** each job gets a live log page with a Stop button (which sends SIGTERM; paid calls already made still cost). When the job finishes, the page shows the saved run's verdict counts and cost.
  - **History:** the page lists jobs started from the dashboard (scheduled ones are labelled "Scheduled ·"), plus every saved run in `out/` (from the dashboard, a shell or cron) with its mode, verdict counts, errors, Exa cost and Claude tokens.
  - **Mechanics:** jobs run `python hunt.py …` in the data folder (`--root`) as a separate process, so they behave exactly like the CLI. Logs go to `jobs/<id>.log` and selected-company lists to `jobs/<id>-companies.csv` (both git-ignored). Only one job runs at a time (see the lock in [Run](../pipeline/README.md#run)). If the dashboard stops while a job runs, the job shows as interrupted after a restart. Ctrl+C in the dashboard's terminal stops the job too. A job that outlives the dashboard (for example after `kill` of the server process) keeps running and holds the lock until it finishes.


The former Inbox page and `/inbox` route are removed. Use Board for scored roles; finished jobs link back to Board sorted by most recent. The watch list (`hunt.py watch`, `[watch]` in `profile.toml`) is removed too: Exa monitors cover new postings at the companies you pick. Watch-list postings you already tracked keep their statuses, notes and titles on Pipeline, read from the `watch_state.json` the watch list left. Email suggestions, mailbox access and the chat bot are unchanged.

The dashboard copies the pipeline files into `hunt.db` (SQLite, git-ignored) and copies them again whenever one of them changes, so a finished run shows up on the next page load. A run directory that cannot be read (for example while a run is still writing it) is skipped with a warning banner and read again once it changes; the banner also reports a `watch_state.json`, `discovered.csv` or `companies.csv` that cannot be read, and an application kit (`kits/<domain>.json`) that is not in the shape `apply-kit` saves, and the pages keep working without it (with `companies.csv` unreadable, Runs counts no companies, a full run cannot be started and **Add to companies.csv** is refused until the file is fixed; Leads still lists every company, none marked as queued). Companies are keyed by their domain as `run` spells it (`runs.normalize_domain`: lower-case, without `https://`, `www.` or a path), so results saved under an older spelling such as `www.Acme.com` and new ones under `acme.com` make one card, and a check-careers status or note saved under the older spelling follows it (a one-time migration of `hunt.db` on the first start). Runs saved before `_run.json` existed show no mode or cost. `hunt.db` also holds your statuses, notes, side projects, job history, answers to email suggestions and the applications you added from email, which exist nowhere else: back it up if they matter, and do not delete it. The database is in SQLite's WAL mode, so the newest changes sit in `hunt.db-wal` and `hunt.db-shm` next to it until a checkpoint: copy or back up `hunt.db` only while the dashboard is stopped, or the copy misses them. The copied pipeline data is rebuilt automatically when needed; your own data is never touched by that.

## MCP endpoint

Optional: with `MCP_TOKEN` set (at least 32 characters; a random one: `python -c "import secrets; print(secrets.token_urlsafe(32))"`), the dashboard also serves an [MCP](https://modelcontextprotocol.io) endpoint at `/mcp`, so an AI client (Claude Code, Claude Desktop, Cursor and others that speak Streamable HTTP) can read what the pages show, change your statuses, notes, lists, projects and interviews, and start jobs, from a chat. Without the variable there is no endpoint; the dashboard refuses to start with a shorter token.

Connect a client with the endpoint's address and the token as a bearer token. Claude Code:

```bash
claude mcp add --transport http job-hunt https://<your domain>/mcp --header "Authorization: Bearer <MCP_TOKEN>"
```

A client configured with JSON (Cursor's `~/.cursor/mcp.json`, for one):

```json
{"mcpServers": {"job-hunt": {"url": "https://<your domain>/mcp", "headers": {"Authorization": "Bearer <MCP_TOKEN>"}}}}
```

Locally the address is `http://127.0.0.1:8000/mcp`.

- **Access.** The endpoint takes `Authorization: Bearer <MCP_TOKEN>` in place of the login and the page's token: the login cookie does not open it, and the bearer token opens nothing else (the pages still ask for the password). Like every request, one to `/mcp` must name an allowed host, and one whose `Origin` names another site is refused. A missing or wrong token gets 401. It takes POST only: it keeps no sessions and answers each request with JSON. Anyone with the token can read your data and start paid jobs, as with the password: keep it to yourself, and change it (on Railway, a variable change and so a redeploy) to lock a client out. A client that can only sign in with OAuth and cannot send a header cannot connect.
- **Reads** (free): `overview` (start here: the latest run, the job running now, problems reading the files, board and pipeline counts, email updates waiting, upcoming interviews), `list_companies` (the board, with the same filters), `get_company`, `list_runs` (with the companies that failed in the latest run), `spend_summary` (the Exa dollars and Claude tokens of the saved runs of the last days, and the jobs by kind and outcome; only `hunt.py run` records costs the dashboard reads, so other jobs are counted, not costed), `list_leads`, `list_monitors` (the Monitors block: each company with whether its monitor is on Exa), `get_pipeline`, `pipeline_funnel` (items per status, applications, responses and response rate, applications per week), `list_email_suggestions`, `list_interviews`, `get_interview` (details, prep brief, review, the transcript's speakers and talk metrics, never what was said), `interview_progress`, `list_projects` (with the scorer's ideas), `list_jobs`, `get_job` (with the end of its log). They read the same copy of the files as the pages, so they show what the pages show.
- **Changes** (free): `set_status` (a status and/or notes, which replace the saved ones), `decide_email_suggestion` (apply, add to the pipeline, dismiss), `queue_leads` (**Add to companies.csv**), `create_project`, `update_project`, `create_interview`. Each does what its button does, with the same checks.
- **Jobs** (what the job costs, as on Runs): `preview_job` takes the choices of the Runs page, the interview pages and a company's details (a run's mode, **With Fiber** and selected companies; a discover's focus and limit; `mail`, `followup`, `news` and `monitor`, each as a dry run or not; `monitor_sync`; `new_monitor` for **New monitor**, `edit_monitor` for **Edit** and `remove_monitors` for **Remove selected…** under Monitors; interview prep and review; `apply_kit` for **Write application kit…**, with the company's domain) and answers as the confirmation dialog does, with the command, the estimated cost and the side effects, plus a token. `start_job` starts that job, and only with that token: a token lasts 15 minutes and starts one job, and a start refused because another command runs leaves it valid. The job is checked again when it starts, as **Start** in the dialog does, and runs like any other: one at a time, listed on Runs (labelled "MCP ·", as scheduled ones are "Scheduled ·"), with its log (`get_job`), and `cancel_job` stops it.
- **What the client sees and does.** Each tool says whether it only reads: clients run those without asking and ask you before each of the others (`start_job` is also marked as reaching beyond the dashboard). The endpoint's instructions tell the model to show you a job's preview and start it only once you agree. What the tools return includes text from web pages and email (research summaries, posting titles, email subjects and summaries, job logs), which the instructions tell the model to treat as data. No tool reads a mailbox, the CV, `profile.toml` or a transcript's words, and none sends anything itself: Telegram only through the jobs that send it from Runs too. Everything the tools return goes to the model your client uses, under its provider's terms: your companies, notes, interview briefs and reviews, email subjects.
- **PostHog**: each call is an event, by the tool's name, and PostHog's MCP Analytics SDK reports each call, handshake and tool listing too, without what a tool was given or answered (see [PostHog events](#posthog-events)). With PostHog on, a client gets a session token in the `Mcp-Session-Id` header at its handshake; some clients then also try `GET /mcp` (a stream) and, when they close, `DELETE /mcp`. Both get 405 and change nothing: calls work as without it.

The dashboard also writes one log record, `dashboard_started`. The job itself reports its own start, end and model calls as `hunt.py` does everywhere (see [PostHog](../clients/README.md#posthog)).

### From page to page

A click on a tab, or on any other link of the dashboard, is the page view of the page it leads to, and `previous_route` is the page the click was made on. **Interviews** clicked on the Board is a `$pageview` of `/interviews` with `previous_route` `/`; clicked on a company's page, one with `/c/{domain}`. The dashboard reads it off the `Referer` header the browser sends with the request and keeps only the route that address matches, never the address.

- A page that is loaded again has its own route as `previous_route`: the reload or redirect that follows an action, and the browser's reload button, which the browser marks with `Cache-Control: max-age=0`. So the page views whose `previous_route` differs from `$pathname` are your moves from one page to another. Two reloads come out differently. A forced reload, the one that skips the browser's cache, is marked `no-cache` instead, like every request made while the developer tools keep the cache off, so it is not taken for a reload and repeats the page the page was first opened from. And a reload that ends on the login page, because the session ran out, says `/login` was opened from `/login`.
- `previous_route` is absent when the page was opened from outside the dashboard: a typed address, a bookmark, a link in Telegram.
- A page the browser shows again from its own copy, as Back and Forward usually do, asks the dashboard for nothing and is not a page view.

### Support widget

Optional, for trying out [PostHog Support](https://posthog.com/docs/support): with `POSTHOG_SUPPORT_WIDGET=1` as well as `POSTHOG_PROJECT_TOKEN` and `POSTHOG_HOST` (the dashboard refuses to start with the first and not the other two), every page behind the login shows Support's chat button, and what you write in it becomes a ticket in the project's Support inbox. Support and its in-app widget are switched on in PostHog itself (**Support → Settings**); the widget's look, greeting and identification form are set there too.

This is the one place where text of yours goes to PostHog: the messages you type, the name and email the widget's form asks for, the browser you use, posthog-js's random session id and, for a new ticket or a ticket recovery (**Recover your tickets**, and the emailed link it sends), the address of the page you started it on (`/c/acme.com` names the company). The widget adds those to its own requests, out of reach of the dashboard's settings. The pages load posthog-js from the project's assets host (`https://eu-assets.i.posthog.com/static/array.js`, always its latest version) only with the setting on, and never on the login page, which is public on Railway. Everything else posthog-js would capture by itself is off (page views and leaves, autocapture, heatmaps, dead clicks, web vitals, exceptions, session recordings, surveys, product tours, feature flags), whatever the project's settings say. The page drops every event but the widget's own (`$conversations_loaded`, `$conversations_widget_loaded`, `$conversations_widget_state_changed`, `$conversations_message_sent` and the like) and takes every address off those (`$current_url`, `$pathname`, `$referrer`, `$session_entry_url`, ...); they are the owner's, with the same distinct id as the dashboard's other events and no person profile. See `posthog_client.support_widget`.

Tickets are tied to the browser: another browser, or cleared site data, starts without them (the widget's **Recover your tickets** sends a link to the email you gave).

## Deploy to Railway

Runs the dashboard on [Railway](https://railway.com), so you can open it from your phone and have it start `discover`, `run` (with its Telegram notification), `monitor`, `mail` and `news` on a schedule. Railway builds the `Dockerfile`: the code lives in `/app`, and your data (the same files as in the project folder) on a volume mounted at `/data`. Railway bills the always-on service and the volume; scheduled commands cost the same Exa and Claude money as from the laptop.

Railway's own cron services cannot share a volume with the dashboard, so the dashboard process starts the scheduled commands itself, as jobs on the Runs page with the same one-at-a-time lock, logs and history.

Upgrading a deployment from before the watch list was removed: delete every `watch` entry from `HUNT_SCHEDULE` first (the dashboard refuses to start with one, see below), and move the companies of `[monitor].companies` in `/data/profile.toml` into `/data/monitors.csv` as `name,domain` rows, then delete that list from the profile (`railway volume browse`). Until then `monitor-sync` changes nothing, and the Runs page cannot add a company while monitors run without a `monitors.csv`.

1. In Railway: **New project → Deploy from GitHub repo**, pick this repository.
2. Attach a volume to the service with mount path `/data` (right-click the service → **Attach volume**, or `railway volume add --mount-path /data`). Without it the service does not start (`--root /data is not a directory`), so a missing volume never silently loses your data on the next deploy.
3. Set the service variables:

   | Variable | Value |
   |---|---|
   | `DASHBOARD_PASSWORD` | Required: the login password, at least 12 characters. A random one: `python -c "import secrets; print(secrets.token_urlsafe(18))"`. Anyone with it can start paid runs, so keep it to yourself. |
   | `EXA_API_KEY`, `ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, optionally `SCORING_MODEL`, `TYPESAFE_API_KEY` and `JEV_MODEL` | As in your `.env` (the container has no `.env`). |
   | `TZ` | Your time zone, for example `Europe/Belgrade`. Schedules and saved-run times use it; default UTC. |
   | `HUNT_SCHEDULE` | Optional: scheduled commands (below). |
   | `OUTLOOK_CLIENT_ID`, optionally `OUTLOOK_TENANT` | Only for email updates and the chat bot: as in your `.env` (see [Email updates](../inbox/README.md#email-updates)). |
   | `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET` | Only for the chat bot's Gmail access: as in your `.env` (see [Chat with your mail](../inbox/README.md#chat-with-your-mail)). |
   | `CHAT_BOT` | `1` keeps the Telegram chat bot (`hunt.py chat`) running alongside the dashboard (see [Chat with your mail](../inbox/README.md#chat-with-your-mail)). A news digest you ask it for uses `EXA_API_KEY` and the volume's `profile.toml` and `news_state.json`, and costs Exa and Claude money each time. |
   | `LOGFIRE_TOKEN` | Optional, with `CHAT_BOT=1`: traces of the bot's answers in Pydantic Logfire, without their text (see [Chat with your mail](../inbox/README.md#chat-with-your-mail)). |
   | `POSTHOG_PROJECT_TOKEN`, `POSTHOG_HOST` | Optional, both or neither: your PostHog project token and its ingestion host (`https://eu.i.posthog.com` or `https://us.i.posthog.com`). The dashboard then reports your actions, the pages you open (by route) and its errors, and the jobs and the chat bot it starts report their commands and model calls, none of it with text (see [PostHog events](#posthog-events)). |
   | `POSTHOG_SUPPORT_WIDGET` | Optional, with both PostHog variables: `1` shows PostHog Support's chat widget on the pages behind the login. What you type in it is sent to PostHog as a ticket (see [Support widget](#support-widget)). |
   | `MCP_TOKEN` | Optional: at least 32 characters. Serves the [MCP endpoint](#mcp-endpoint) at `https://<RAILWAY_PUBLIC_DOMAIN>/mcp` for AI clients that send it as a bearer token. Like the password, it lets whoever has it read your data and start paid jobs. A random one: `python -c "import secrets; print(secrets.token_urlsafe(32))"`. |
   | `DASHBOARD_URL` | Only for a custom domain. Without it, Telegram links point to `https://<RAILWAY_PUBLIC_DOMAIN>`. |

4. **Settings → Networking → Generate domain.** Railway sets `RAILWAY_PUBLIC_DOMAIN`, which the dashboard accepts as its host name.
5. Upload your files to the volume with the [Railway CLI](https://docs.railway.com/cli/volume) (volume paths start at `/data`, so `/profile.toml` is `/data/profile.toml`):

   ```bash
   railway volume files upload profile.toml /profile.toml
   railway volume files upload cv.md /cv.md              # paths in profile.toml are relative to /data
   railway volume files upload companies.csv /companies.csv
   # optional: your history, so nothing is reported or suggested twice
   railway volume files upload discovered.csv /discovered.csv
   railway volume files upload monitors.csv /monitors.csv      # the companies your Exa monitors watch (see below)
   railway volume files upload out /out
   # optional: email updates and the chat bot (see Email updates and Chat with your mail in inbox/README.md), and their history
   railway volume files upload outlook_token.json /outlook_token.json
   railway volume files upload gmail_token.json /gmail_token.json
   railway volume files upload mail_state.json /mail_state.json
   railway volume files upload news_state.json /news_state.json
   ```

   `railway volume browse` opens an interactive browser for editing these files later (for example to remove a company from `companies.csv`). To keep your statuses, notes and side projects, stop the local dashboard, then `railway volume files upload --overwrite hunt.db /hunt.db` while no job runs on Railway, and restart the service (**Deployments → Restart**).
6. Open the domain, log in, and check the Runs page: the Schedule section lists what will run and when, and with `CHAT_BOT=1` the Chat bot section shows the bot running (since when, how many starts, the tail of its output). The dashboard starts `hunt.py chat` when it starts, restarts it whenever it exits (after 10 seconds, then 1 and 5 minutes while it keeps exiting soon after starting, for example without a signed-in mailbox), and stops it at shutdown; its output goes to `jobs/chat.log` on the volume, truncated at each dashboard start. The bot is not a job: it holds no lock, so scheduled commands and Run buttons work as before.

`HUNT_SCHEDULE` holds one entry per line, or entries separated by `;` (easier in Railway's variable editor): five cron fields (minute, hour, day of month, month, day of week with 0 or 7 for Sunday; numbers, `*`, ranges, lists and `*/n` steps), then a `hunt.py` command. Supported commands: `run`, `run --dry-run`, `run --research-only`, each also with `--fiber` (Fiber's jobs database as well, paid per company), `discover [focus] [--limit N]`, `mail`, `followup`, `news` and `monitor`, the last four also with `--dry-run`, and `monitor-sync`. `watch` and `send` are not among them: an entry with `watch`, left from before the watch list was removed, stops the dashboard from starting until you delete it. For example, discovery every Monday at 07:00, a scored run with its Telegram notification every day at 07:30, email every 2 hours from 08:00 to 20:00, the news digest on Mondays at 08:30, what your Exa monitors found at 08:00, 12:00, 16:00 and 20:00, and the applications that have waited 8 days for a reply every day at 09:00:

```
0 7 * * 1 discover --limit 15; 30 7 * * * run; 0 8-20/2 * * * mail; 30 8 * * 1 news; 0 8,12,16,20 * * * monitor; 0 9 * * * followup
```

An entry that is not valid stops the dashboard from starting, with the reason in the deploy logs. A command that comes due while another one runs waits and starts as soon as that one finishes; one that cannot start (for example `companies.csv` is empty) shows the reason on the Runs page and in the logs. Commands due while the service is down (during a redeploy) are skipped, not caught up. Changing a variable redeploys the service, which interrupts a running job. `discover` only adds leads: use **Add to companies.csv** on Leads so the next scheduled `run` researches them.

Railway and a laptop do not share files: once Railway runs `monitor` on a schedule, remove the laptop's cron entry, or both will send the same postings. `monitor-sync` belongs where `monitor` runs: add, edit and remove companies under Monitors on the Runs page here, since `monitors.csv` and `monitor_state.json` on the volume are what tell the sync and `monitor` which Exa monitors to keep and read. Railway can [back up the volume](https://docs.railway.com/volumes/backups); `railway volume files download /hunt.db` copies your tracking data to the laptop. Do either while the service is stopped (or at least no dashboard is running): the dashboard keeps the newest changes in `hunt.db-wal` until a checkpoint, and a copy of `hunt.db` taken while it runs misses them.

`monitor_state.json` also marks which monitors on your Exa account are this folder's. Keep one copy in use: to move the monitors from the laptop to Railway, upload it with `monitors.csv` (`railway volume files upload monitor_state.json /monitor_state.json`) and stop running `monitor-sync` on the laptop, or each copy deletes what the other created (see [Monitors](../pipeline/README.md#monitors)). The list used to be `[monitor].companies` in `profile.toml`: while the volume's profile still has it, `monitor-sync` (and so the sync of **New monitor**, **Edit** and **Remove selected…**) changes nothing and says so in its job log; move the companies to `/monitors.csv` (`railway volume browse`) and delete the list from the profile.

To try the image on the laptop, from the project folder: `docker build -t hunt . && docker run -p 8000:8000 -e DASHBOARD_PASSWORD=… -v "$PWD":/data hunt`, then open `http://127.0.0.1:8000`. The container reads and writes the project folder's data files, and its jobs see only the keys you pass with `-e`.
