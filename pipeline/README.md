# Job-hunt pipeline

The job hunt itself: finding companies, researching them with Exa, reading their job boards, screening roles with Jev and scoring fit with Claude, watching a few companies for new postings and the news digest. `hunt.py` at the repo root runs all of it.

## Files

| File | Purpose |
|---|---|
| `research.py` | Per-company Exa research (identity, signals, open roles), open roles from the company's job board, posting link checks |
| `scoring.py` | Jev role screen and Claude fit scoring (structured output) |
| `monitor.py` | New postings at the companies in `monitors.csv`: read from the company's job board, or found by an Exa monitor that is kept in step with the list and your roles; what is new since the last check; `monitor_state.json` |
| `news.py` | News digest: Exa news search per topic, Jev's relevance screen, Claude's picks, `news_state.json` |
| `kit.py` | Application kit: one Claude call that drafts the answers to a posting's application questions, a note and the CV points to lead with |
| `runs.py` | Saved-run format, the posting links the saved runs hold per company, the domain normaliser, the `monitors.csv` list, the application kit files (`kits/<domain>.json`) and the one-command-at-a-time lock, shared by `hunt.py` and the dashboard (`out/<timestamp>/`, `_run.json`, `.hunt.lock`) |

## Run

```bash
python hunt.py discover --limit 20             # suggests name,domain,why rows; logs them to discovered.csv
python hunt.py discover "fintech" --limit 20   # same, with an extra focus
python hunt.py run --research-only             # Exa only: no Claude, no Telegram
python hunt.py run --dry-run                   # research + score, print the full digest
python hunt.py run                             # research + score + send the notification to Telegram
python hunt.py run --fiber --dry-run           # any mode: also ask Fiber's jobs database for open roles (paid agent runs)
python hunt.py send                            # send the latest saved run's notification to Telegram (no new research or scoring)
python hunt.py monitor-sync                    # watch each company in monitors.csv: read its job board, or keep an Exa monitor for it (Exa runs them every 12 hours)
python hunt.py monitor                         # send the suitable new postings the boards and the monitors found to Telegram (Claude)
python hunt.py outlook-login                   # sign in to Outlook once (read, create drafts), for `mail` and `chat`
python hunt.py mail                            # application confirmations, rejections and interview invites in new email: Telegram + dashboard suggestions (Claude)
python hunt.py news                            # news digest on your [news].topics to Telegram (Exa + Claude)
python hunt.py interview-prep interviews/<id>  # prep brief for one interview (Claude; see interview/README.md)
python hunt.py interview-review interviews/<id> # review one interview's transcript (Claude; see interview/README.md)
python hunt.py apply-kit acme.com              # application kit for the company's best role: form answers, a note, CV points (Claude; see Application kit below)
python hunt.py gmail-login                     # sign in to Gmail once (read, create drafts), for `chat`
python hunt.py chat                            # Telegram chat bot over your mail: summaries, search, reply drafts; news digests on request (Claude, Exa; see inbox/README.md)
python -m dashboard                            # dashboard at http://127.0.0.1:8000: results, your tracking, starting runs (see dashboard/README.md)
```

Options (`python hunt.py <command> --help` lists them): `--profile FILE` before the command reads another profile (default `profile.toml`); `run --companies FILE` (default `companies.csv`) and `run --fiber` (see Fiber as a role source, below); `discover --limit N` (default 15) and `--history FILE` (default `discovered.csv`); `send [DIR]` (a directory under `out/`, default the latest run); `monitor-sync --companies FILE` (default `monitors.csv`); `monitor-sync --state FILE` and `monitor --state FILE` (default `monitor_state.json`); `outlook-login --token FILE` and `mail --token FILE` (default `outlook_token.json`); `mail --state FILE` (default `mail_state.json`) and `--days N` (default 14); `news --state FILE` (default `news_state.json`) and `--days N` (default 7); `gmail-login --token FILE` (default `gmail_token.json`); `chat --outlook-token FILE` and `--gmail-token FILE` (the two sign-in files) and `--news-state FILE` (default `news_state.json`, shared with `news`). `run`, `monitor`, `mail` and `news` take `--dry-run`.

Each run saves raw research and scores to `out/<timestamp>/<domain>.json` (with the Jev screen of each role in `screen`, see [Jev screening](../clients/README.md#jev-screening), postings found only on third-party sites in `third_party_roles`, see Third-party sites below, and any research warnings, such as a failed ATS fallback search, in `warnings`), plus `out/<timestamp>/_run.json` with the run's mode (`research_only`, `dry_run` or `deliver`), whether it asked Fiber (`fiber`), start and save times, company and error counts, the Exa cost summary and, for scored runs, the scoring model and Claude token totals and, when `TYPESAFE_API_KEY` is set, the Jev model, requests, input tokens and dollars (`jev`). It also prints Exa cost, Claude token usage and Jev usage; a company's third-party listings and research warnings are printed under it in the digest and in the `--research-only` output. A failing company is reported in the digest and does not abort the run (exit code 1 if any failed). Missing keys are detected before any paid call: `run`, `discover` and `news` refuse to start without `EXA_API_KEY` (so does `interview-prep` when it would fetch the posting), and the same check covers `ANTHROPIC_API_KEY` and the Telegram values for the commands that use them.

One `hunt.py` command runs at a time per project folder: each command holds a lock (`.hunt.lock`, git-ignored) while it runs, and a second one exits at once with "Another hunt.py command is running here". This covers commands from a shell, cron and the dashboard alike. A cron `monitor` that starts during a run exits with that message and checks again at its next scheduled time. The OS releases the lock when a command exits, so a crashed command never leaves it stuck. Three commands do not hold the lock: `outlook-login` can wait up to 15 minutes for you to sign in in the browser and touches only `outlook_token.json`, so it only refuses to start while another command runs; `gmail-login` touches only `gmail_token.json`, which no other command rewrites; and `chat` runs for as long as you leave it and shares two files with the other commands: `outlook_token.json` and, when you ask it for news on your topics, `news_state.json` (see [Chat with your mail](../inbox/README.md#chat-with-your-mail)).

The Telegram notification is short: the digest's count header, one entry per apply, consider and stretch role (score, verdict, company, role title and posting URL, so it works away from the laptop), the names of failed companies, and a link to the dashboard (`DASHBOARD_URL` in `.env`; default `https://<RAILWAY_PUBLIC_DOMAIN>` on Railway, otherwise `http://127.0.0.1:8000`). Reasons, concerns, gap notes and side-project ideas are in the dashboard and in the `--dry-run` digest.

`send` rebuilds the notification from a saved run in `out/` (latest by default, or pass a directory). Use it after a `--dry-run` so what is delivered comes from the run you reviewed, without paying for a second run. The Telegram header carries the saved run's date, not the day you send it: from `_run.json`, or from the folder name when the run has no readable manifest (older runs, or one interrupted while saving); a directory you picked that has neither is dated today.

Discovery runs one search per target role plus one deep search (6 searches, roughly $0.15-0.20 for `--limit 20`) because a single search returns only a handful of companies. Results are merged round-robin, filtered (job boards and anonymous employers dropped, `[search].exclude_domains` removed) and appended to `discovered.csv` (`discovered_at,name,domain,why,focus`). Domains already in the history are skipped, so repeated runs only return new companies. The printed `name,domain,why` rows load as `companies.csv` rows (extra columns are ignored); `discovered.csv` adds `discovered_at` and `focus` around them. The `why` column is Exa's unverified claim; `run` is what actually researches and scores each company.

Scoring model: `claude-sonnet-5-5` by default, override with `SCORING_MODEL` in `.env`.

Role screen (with `TYPESAFE_API_KEY`): before Claude, Jev answers yes/no and rubric questions about each open role (one request per role, given your target roles and `location`): is it one of your target roles, its seniority level (junior, mid, senior, lead or above), does the posting limit the role to regions that exclude your location, is it on-site or hybrid only, is the office in your country, and does it offer relocation. A role is dropped only when Jev is confident it fails a hard rule of the rubric: not a target role (probability 0.1 or less), junior or mid-level (0.9 or more; like the scoring rubric, the screen counts senior and above, whatever `[search].seniority` lists), or no relocation (0.1 or less) together with a region that excludes you (0.9 or more) or an on-site or hybrid office outside your country. Claude scores the company with the remaining roles; when no role remains, the company is a **skip** with score 0 and, as concerns, what each role failed (at most three: with more than three roles, two roles and a "<n> more open roles also failed the screen" line), and Claude is not called. The location questions are skipped when `location` is empty. Each role's answers and failures are saved under `screen` in `out/`, for tuning the thresholds (`scoring.SCREEN_YES`, `SCREEN_NO`, `BELOW_SENIOR_MIN`). Companies without open roles are not screened.

Model-quality exam: `python -m evals roles` checks nine public, human-labeled synthetic postings for free. Explicit `--live --output NEW_DIRECTORY` evaluates this same production screen on Jev and saves per-case evidence, separate calibration/holdout counts, and a readable report; it does not run the rest of the pipeline. See [AI evaluations](../evals/README.md) for paid-call approval, publication, and the small dataset's limits.

Importing the Jev screen does not load Exa or `.env`. The research module used for posting-link checks is imported only inside `score_company`, keeping the standalone eval's environment-only credential boundary intact.

Verdicts in the digest: **apply** (score 75+), **consider** (50-74), **stretch** (a role centred on one of your declared gaps; see below), **check careers** (no live posting to apply to: either the company scores 50+ on its own, or a role that fits was seen only on a third-party site; look at its careers page), **skip** (below 50, identity not verified, the posting excludes your location without relocation support, or score 0 when the Jev screen dropped every open role and no third-party listing is left). A live posting on the company's own site or a job board it posts on is required for apply/consider/stretch.

Stretch: list areas where your experience is thin in `[candidate].gaps` (for example growth engineering with about 6 months of experience). When a posting's core work falls in such an area, the digest shows **STRETCH** instead of apply, with a `Gap:` line stating what you have, up to two `Build:` side-project ideas that would build credible proof, and a score reduced for the gap. Roles outside the gaps are unaffected.

Weak spots and scope: `[candidate].weak_spots` lists specific tools you are weak in (for example PySpark). If a posting requires one, the digest adds it as a concern and gives one preparation step in `Next:`; unlike a gap, it does not change the verdict. When a posting's title and duties disagree (an analyst title with ETL/dbt work, say), the digest adds a `* Scope:` line saying which part of your background fits. The scorer reports compensation only as stated in the posting and never judges whether it is high or low.

Role search: the main Exa call looks for postings and is asked for each one's link on the company's own careers site or its job board. For a verified company, a second call restricted to the company's own domain and ATS/job-board domains (Ashby, Greenhouse and Lever with their EU hosts, Workable, SmartRecruiters, Recruitee, Teamtailor, Personio, Pinpoint) runs when no live role is left, or when the main call lists a posting on a third-party site; it costs about $0.007 extra and adds the postings not listed yet. Only postings Exa marks as belonging to the company are kept; `role_source` in `out/` records which source supplied them (`main`, `board`, `board+main`, `fiber`, `fiber+main`, `ats_fallback`, `none`, or `main+ats_fallback` and the like when the second call added to what was there). The research step only quotes what each posting says about remote regions and relocation; judging eligibility for your `location` is the scorer's job.

Job boards: Ashby, Greenhouse, Lever, Workable, SmartRecruiters, Recruitee, Teamtailor, Personio and Pinpoint publish each company's board as a feed that needs no key and lists every posting that is open (`clients/boards.py`). When a verified company's board is known, the run reads it, free, and neither the second call nor Fiber is asked for that company.

- **Which board.** The one a posting link of the company names: a link the main call returned (a dead one too), or one an earlier run saved for the company in `out/`, when that run's research verified the company (an unverified result is where a namesake's postings are saved). So a company's first run can still go through the searches, and its later runs read the board. The board has to carry the company's name: its name on the board, letters and digits only, is the company's name, the name its domain is registered under, or the domain whole (`acme`, or `acmeio` for acme.io). A board named anything else (`acme-labs`, `acmepay`) is left to the searches: a search that takes another company's posting for this one's must not bring that company's whole board with it. A site under another's name is not registered under the company's: for `acme.github.io` the board named `github` is GitHub's, and only the company's name names its board. Letters of any alphabet count, so the board named `ber` is not Über's. Of the 23 boards that the links in saved runs named, 22 carried the name this way. What the rule cannot tell apart is two companies of the same name: a verified company whose search returns a link to its namesake's board gets that board.
- **What you get.** The board's postings whose title holds every word of one of your target roles, in any order ("Senior Engineer, Data Platform" for `data engineer`, not "Data Engineering Manager"), and the board's posting for each third-party listing the main call saw (one whose title holds the listing's). Each is live without a link check, since the board lists only open postings, and comes with the board's own text of the posting, so none is fetched for it (SmartRecruiters' list has no text: its postings are fetched like any other). Up to 8 roles, joined with the main call's as Fiber's are: titles that name one of your seniority levels first, the board's postings before the main call's that the board does not list, and a posting both list under the main call's link, which is the one earlier runs saved. The Jev screen and the scorer judge seniority, location and fit as before.
- **One posting, several links.** A link on one of these boards counts by the board's own id for the posting, whatever form it takes: `apply.workable.com/j/<id>` and `apply.workable.com/acme/j/<id>`, Lever's `/apply`, Greenhouse's old and new hosts, and a careers page that carries the id (`?gh_jid=<id>`, `?ashby_jid=<id>`, or a path that ends in an Ashby or Lever id).
- **When a board is not read.** A board that does not answer, or answers with something else than its feed, is a research warning ("Job board could not be read"), and the second call and Fiber work as before. A board that lists no posting at all does not count either: a company that moved to another job board leaves an empty one behind. A posting the board keeps off its list (Ashby's unlisted postings, open by a direct link only) is not one of its roles, though a link to it checks as live. A company whose identity is not verified gets no board, as it gets no second call.
- **How it compares.** Checked against the saved runs of November 2026: 18 of 30 researched companies had a posting link on one of these boards, and the feeds of 16 answered at once, most in under a second. They listed 31 postings with a target role in the title. Of the 20 that were already open at the company's last run, the runs had listed 8. Of the 45 board links those runs had saved, 12 were still open.

Third-party sites: a link counts as a posting only where the company posts its jobs itself: its own domain (subdomains included), one of the job-board hosts above, or a site registered under its name on another domain, either the name alone (`acme.de`, `careers.acme.eu` for `acme.com`) or with a careers word after a hyphen (`acme-jobs.com`, `careers-acme.io`). Any other site is a third party, such as an aggregator or a recruiter's board: its page can ask for an account or payment before it shows where to apply, and can answer for a job that has closed or was never the company's. In seven runs saved before this rule, 18 of the 47 apply, consider and stretch roles pointed at such pages.

- **What happens to the link.** It is never an open role. The second search is given the posting's title and looks for it on the company's own site and job boards. A posting found there whose title holds the listing's ("Senior Data Analyst (Remote, EU)" for "Senior Data Analyst", not "Data Analyst") takes its place. A listing that is not found is a lead: saved in `third_party_roles`, printed as `third-party listing:` under the company, and shown in the dashboard's company details under "Seen only on third-party sites" (the card carries a "third-party listing" tag). A role without a web link, or with one written to read like the company's (`acme.com@other.io`), is left out.
- **Verdict.** The scorer sees the leads next to the open roles and is told never to offer one as the role to apply to. When no open role fits and a lead does, the company is check careers whatever its score, with the lead's title as the role to look for and no link. `score_company` holds Claude to it: a best role whose link is not one of the open roles (a lead, a page the research cited, another company's posting, a role the Jev screen dropped) loses the link, and apply, consider or stretch for it becomes check careers. A company whose open roles all fail the Jev screen goes to Claude, failed roles included, when a lead is left: one Claude call where there was none, for a check careers or a skip.
- **Link check.** A third-party link gets the free check only: a dead or closed one goes to `dead_roles`, and no paid fetch settles an unclear one.
- **Cost.** The second search (about $0.007) runs for every verified company with a lead that no open role stands for, on each run until one does.
- **Results saved before the rule** keep their third-party links as roles until the company is researched again.
- **Limits.** A company whose careers site is on a domain that does not carry its name this way (`metacareers.com`, a subsidiary's `acme-digital.de`, `someone.acme.site`), or on a job board not in the list (Workday, BambooHR), gets its postings listed as leads. A company name shorter than four letters counts on its own domain only. A third-party site registered under the company's name passes as the company's own (`remote.co` or `remote-jobs.io` for `remote.com`).

Fiber as a role source: with `run --fiber` (on the dashboard: **With Fiber** on the Runs page or in a run's confirmation; in `HUNT_SCHEDULE`: `run --fiber`), each verified company's open postings are also asked from [Fiber.ai](https://exa.ai/docs/agent/connect/fiber)'s jobs database, through one Exa agent run. A company whose job board is read (see Job boards, above) is not asked: the board is its whole list, and free. Without Fiber, open roles come from the two calls above. It is chosen per run: `[search].role_source` in `profile.toml`, which turned it on before, is no longer read, and a profile that still has it gets a warning.

- **What you get.** Up to 8 roles: live links first, Fiber's before the main search's that Fiber does not list, then unverified links in the same order, so an unverified link never pushes out a live one. A failed Fiber search is a research warning and the main search's roles stand; when Fiber has none, the main search and the ATS fallback work as before.
- **One posting, two links.** A posting both sources list appears once, under the main search's link unless only Fiber's is live: the dashboard keeps your status and note by link, so turning Fiber on does not move a posting you already track. Links count as one posting whatever the letter case, `www.`, a trailing slash, `utm_` parameters or Ashby's `/application` suffix, and when both carry the job board's id for it (see One posting, several links, above). A posting named in another query parameter (`?job=123`) or the fragment stays its own, which also means two links that differ in another tracking parameter or a `#section` are listed twice, and so is a careers-page copy of a board posting that does not carry the board's id.
- **Seniority.** It asks for your target roles at any seniority: asked for senior roles only, the agent leaves out postings whose title does not say so. The Jev screen and the scorer judge seniority as before.
- **Which links are kept.** Only postings where the company posts its jobs itself (see Third-party sites, above); Fiber's other links are left out and not kept as leads. An aggregator's page answers 200 for a job that has closed or was never the company's, so the link check cannot catch it: in the first trial five of the six postings listed for one company were such copies. The cost of the rule: a company whose careers site is on a domain without its name, or on a job board not in the list (Workday), loses its Fiber postings, and the main search's still apply.
- **Cost.** The run is $0.025 and Fiber bills per search and per result: $0.09 to $0.40 a company so far, against about $0.01 for the main search. A company with no matching posting still cost $0.09 to $0.21 in the trial, well over the run's own price, although Exa's docs say a Fiber call that returns nothing is free. `run` prints a line about it before it starts, and the cost is part of the run's Exa total. The Runs page estimates a run with Fiber from the saved runs with Fiber and a run without it from the runs without (`fiber` in `_run.json`; a run saved before that field counts as one with Fiber when it paid for an agent run); until a run with Fiber is saved, it adds $0.09 to $0.40 a company to the estimate without Fiber. Ctrl-C cancels the agent runs that are still going; stopping the job from the dashboard kills the process, and those runs are billed to their end.
- **Is it worth it.** In a trial on four companies with public Ashby boards (the board is the ground truth), the main search found 2 of the 7 open postings whose title matched the target roles and Fiber mode 6 of 7, all with live links. Four companies is a small sample, and neither source returns the same postings twice in a row. A company with such a board is now read from the board itself: Fiber is for the companies without a board that can be read.

Link verification: Exa often returns stale posting URLs (about 30% were dead in one run, including top-scored roles), so every posting is checked before scoring and dead ones are dropped (recorded as `dead_roles` in `out/`). Ashby (`jobs.ashbyhq.com`) answers HTTP 200 for any URL, so its links are checked against Ashby's public posting API, which lists only open jobs. For other sites, 404/410 or a redirect away from the posting (a soft 404, e.g. Workable `?not_found=true`, Greenhouse `?error=true`) means dead, and so does a page that answers 200 and says the posting has closed. The check reads the text the page shows as it loads (no scripts, styles or comments, and nothing in an element that is hidden or left to a script to show: the `hidden` attribute, `display: none`, classes such as `d-none`, `v-if` or `x-show`, `aria-hidden`, dialogs and templates) for a sentence that is, from its start to its end or a comma, one of the wordings seen in saved runs: "This position is no longer active" on Teamtailor sites, "Sorry, this position has been filled" on SuccessFactors, "Job listing has expired", "This job is no longer available" (`research.CLOSED_RE`). The same words inside another sentence ("until the position has been filled", "This role is no longer available as a remote position") do not count. A URL that is only a board or careers homepage, a check that is blocked or times out, or a redirect to a login or a bot check (one that carries the posting's address along; it used to count as live without the posting being seen) is resolved with a fresh Exa fetch (about $0.001 per link); if that cannot confirm it either, the role is kept as `link_status: "unverified"` and the scorer tells you to confirm it. If every link for a company is dead, the ATS fallback search runs, and a company with no live role becomes "check careers". Not covered: a closed posting whose page says so in other words, in another language, or only once its JavaScript has run (Workday); and a notice that a page carries for other postings and hides with a class of its own style sheet counts as shown. An open posting whose link redirects to an address that no longer holds the link's last path part (a renamed slug) still counts as dead, as before.

Posting text: for up to 3 live roles per company that have none yet, the posting text (first 4,000 characters, about $0.001 per page) is fetched and given to the scorer, because search summaries rarely contain responsibilities and required tools. Without it most concerns read "responsibilities not in the evidence". A role from a job board's feed comes with the board's text and is not fetched; roles whose link is only unverified are not fetched either.

Known limits: Exa is a search engine, not a jobs feed. For a company whose job board is not read, open-role coverage varies between runs, and "no roles found" does not mean no roles exist. A posting found only on a third-party job board (for example a VC portfolio board) is a lead to look for on the company's careers page, not a posting. Treat the digest as leads and confirm on the company's careers page. A board is matched to your roles by the words of each title: a posting titled in other words ("BI Developer" for `data analyst`) is not taken from the board, and reaches you only when the main call lists it. Add the wording to `[search].roles` to have it read.

Score noise: the scoring model does not accept a temperature setting (`temperature is deprecated for this model`), so the same research can score differently between runs: typically within a few points, occasionally more. Verdict thresholds (75, 50) and the gap rule make borderline companies flip (one company went from 68 stretch to 82 apply on identical input). Read scores as bands, not exact values.

## Monitors

For a few companies whose new postings you want to hear about, list them in `monitors.csv` (`name,domain` rows read like `companies.csv`; `cp monitors.example.csv monitors.csv`), or add, edit and remove them under Monitors on the dashboard's Runs page (**New monitor**, **Edit**, **Remove selected…**), which changes the rows and starts `monitor-sync` (see [Dashboard](../dashboard/README.md#dashboard)). Each company is watched in one of two ways. One whose job board has a public feed (see Job boards in [Run](#run)) is read from the board, free: it lists every posting that is open, so none is late or missed. Every other company gets an [Exa Monitor](https://exa.ai/docs/monitors/quickstart): a search for the company's new job openings in your target roles that Exa runs by itself every 12 hours and that returns only the pages its earlier runs did not. Two commands work with them:

- `python hunt.py monitor-sync` settles how each company is watched and makes the monitors on your Exa account match the list. It creates the missing ones, updates those whose search no longer matches (the company's name, your `[search].roles`), deletes those of companies you removed and of companies it reads from their board, and prints when each runs next. Run it after every change to the list or to your roles: the dashboard's Monitors block runs it for you after each change it makes, and a `monitor-sync` entry in `HUNT_SCHEDULE` keeps a removed company, a change of roles or a board that went quiet from waiting for the next one.
- `python hunt.py monitor` reads what the boards list and what the monitors' runs found since the last check, judges each new posting and sends the ones that suit you to Telegram. Schedule it for the times you want to hear about them.

For 08:00, 12:00, 16:00 and 20:00, add this entry to `HUNT_SCHEDULE` on Railway (see [Deploy to Railway](../dashboard/README.md#deploy-to-railway)), or `0 8,12,16,20 * * * cd /path/to/job-hunt && .venv/bin/python hunt.py monitor >> monitor.log 2>&1` to `crontab -e` on a laptop that is on:

```
0 8,12,16,20 * * * monitor
```

The message lists the postings best first:

```
Monitors: 1 new posting(s) for you

[82] APPLY Acme: Senior Analytics Engineer
https://jobs.ashbyhq.com/acme/1111
```

- **A company read from its job board.** `monitor-sync` reads a company from its board when a posting link of the company names one (a posting a check judged, or a link a saved run that verified the company holds for it in `out/`), the board carries the company's name (see Which board in [Run](#run)), and its feed answers and lists at least one posting. The company then has no monitor, and the one it had is deleted, with the postings judged for it kept. At each check, `monitor` takes the board's postings in your target roles (by the words of their titles, as in a run) that no check has judged. The first check of a board therefore also finds the postings that were open before it, which a monitor never reports: at most 8 a check, titles that name one of your seniority levels first, the others at the next checks. A posting on the board is live without a link check and comes with the board's text. A board that cannot be read is reported and read again by the next check; nothing is written off. A board that no longer exists is reported at every check until `monitor-sync` runs, and a board that lists no posting any more is quiet until then: at that sync the company gets a monitor again (a company that moved to another job board leaves an empty one behind), and goes back to its board when the board lists a posting. A board that does not answer during a sync is not taken for an empty one: a company that is read from it stays on it, the sync says so in a line, and the next sync reads the board again, so an outage at a job board moves no company from its board to a monitor. Two things still happen during an outage: a company you add while its board does not answer gets a monitor, which the next sync that can read the board deletes, and a company whose links name a second board of its name moves to that one when it lists a posting.
- **What a monitor searches.** "New job openings at Acme (acme.com) for any of: <your target roles>", restricted to the company's own domain and the job-board hosts of Role search (see [Run](#run)), 10 pages a run. The answer is a list of postings (title, link, location, remote or relocation, and whether the posting is the company's) with each new page's text. Seniority and location stay out of the query, as with Fiber: the screen and the scorer judge them.
- **When a monitor runs.** Exa picks the time. In the first trials a new monitor's first run was set between 9 and 72 minutes after it was created; the next ones follow every 12 hours, each up to 30 minutes late (Exa's docs). The period is `PERIOD` in `monitor.py`; after a change to it, the next `monitor-sync` moves every monitor to the new period. Exa then sets each one's next run itself: when the period went from 4 to 12 hours, some monitors kept the run already set and the others got one up to 12 hours after the update. A monitor cannot be set to a time of day, and each company's has its own cycle. That is why the Telegram message comes from the scheduled `monitor` and not from Exa: a posting a run finds at 21:00 is reported by the next check, at 08:00 with the schedule above.
- **What counts as a new posting.** One that Exa marked as the company's, whose link is on a site where the company posts its jobs itself (see Third-party sites in [Run](#run)), is not closed and was not judged by an earlier check. Two links are one posting as they are for Fiber: whatever the letter case, `www.`, Ashby's `/application` suffix, or when both carry the job board's id. The link check is the free one of a run. A link it cannot settle (a bot check, a timeout) is judged as unverified, so at most consider, with a note to confirm it: no paid fetch decides it as in a run, because a posting is judged once here and a fetch that failed would write a new posting off for good. A link that is closed is remembered as closed and not looked at again.
- **Is it suitable.** Each new posting is judged by itself, like a company's best role in a `run`: the Jev role screen when `TYPESAFE_API_KEY` is set, then Claude's fit score against your profile and CV, with the posting's text. The text is the board's, or the one the monitor's run fetched; when the run found the careers page and not the posting's own, it is fetched for every new posting with a live link (about $0.001 each), and a posting without a text is judged on its title and location. Apply, consider and stretch postings are sent; the reasons and concerns for every posting are printed (the job's log on the dashboard). The scorer is told nothing about the company here but its name, so a posting can score lower than in a `run`, which also weighs funding and data-team signals.
- **State.** `monitor_state.json` holds each company's monitor id, the search it was created with and the last run read, or the job board it is read from and since when, and every posting judged, with its verdict and score. It is saved only after a successful send, so a failed send is judged and sent again by the next check, and so is a check that is stopped halfway; `--dry-run` prints the message and saves nothing. A posting whose scoring failed is read again by the next two checks and then given up (remembered as unscored); the others are not judged twice. Railway and a laptop do not share files: run `monitor-sync` and `monitor` in one place. A file that is not valid stops both commands with its name.
- **Whose a monitor is.** Each monitor carries the company's domain and the id of the data folder that created it, which the first `monitor-sync` makes up and keeps in `monitor_state.json`. A monitor of this folder that the file does not list (the reply to a create was lost, or the file is an older copy) is taken over by its company at the next `monitor-sync`, or deleted when nothing lists it, so a company never has two and none runs unaccounted for. Monitors created under another folder's id are never taken over, changed or deleted: they are another data folder's (a trial on the laptop next to Railway), or this folder's from before `monitor_state.json` was lost. `monitor-sync` reports each of them and exits 1, since they are billed like the others: remove them with `monitor-sync` in the folder that created them (after emptying its `monitors.csv`), or on [Exa's dashboard](https://dashboard.exa.ai). Without the file, `monitor-sync` starts over with new monitors, and the postings judged before are forgotten. When Exa cannot list the account's monitors, `monitor-sync` changes nothing.
- **The list.** `monitor-sync` deletes the monitor of every company `monitors.csv` leaves out, so it never skips a row: a row without a name (or with one over 100 characters), a domain that is not a bare host name such as `acme.com`, or a domain listed twice stops it with the row named, and so does a missing `monitors.csv` while monitors run on Exa (an empty file deletes them all). **New monitor** and **Edit** on the dashboard refuse the same rows and, while monitors run without a `monitors.csv`, New adds nothing. Edit and Remove rewrite only the rows they change, and write the file whole at once, so a crash never leaves half a list. The list used to be `[monitor].companies` in `profile.toml`: while the profile still has one, `monitor-sync` stops before any change and asks you to move each company to `monitors.csv` as a `name,domain` row.
- **One copy of the file.** The folder's id travels with `monitor_state.json`. Two copies in use (the laptop's, and one uploaded to Railway) count as one folder: each copy's `monitor-sync` deletes the monitors the other has created since, as its own that nothing lists. To move the monitors to another place, move the file there and stop using the old copy.
- **The webhook Exa asks for.** Every monitor needs a public HTTPS webhook address, and Exa refuses `localhost`. `monitor-sync` gives it the dashboard's address (`DASHBOARD_URL`, or the Railway domain) and subscribes it to the monitor's deletion only, so nothing is sent there while a monitor runs: the runs are read through Exa's API. Off Railway, set `DASHBOARD_URL` in `.env` to a public HTTPS address of yours before the first `monitor-sync`. A sync in which every company is read from its board creates no monitor and needs no address.
- **Cost.** A company read from its job board costs nothing to watch. For the others Exa bills each run $0.002 (up to 10 pages), two runs a day: about $0.12 a month per company. `monitor-sync`, reading the boards and reading the runs are free. `monitor` pays for new postings only: one Jev request each and, unless Jev rules the posting out, one Claude call each (about $0.014, the call a company gets in a `run`). The first check after a company moves to its board pays for every posting in your target roles that is open there.
- **Limits.** Exa is a search index, not a jobs feed: a run finds a posting only after Exa has indexed its page, so a posting can be reported late or not at all, and "nothing new" does not mean nothing opened. Each run searches recent content only (Exa's docs: a run "filters by time"), so a posting that was already open when the monitor was created is never reported: `run` researches a company's open roles. A company read from its board has neither limit, and one of its own: a posting whose title does not hold a target role's words is not taken from the board. The three runs of the first trial (two over 4 hours and one over 7 days, for a company with a large job board) returned no page; the monitors in use since have, each page crawled by Exa between a few hours and a day and a half before the run that returned it. `monitor` reports what went wrong and then exits 1 (a failed job on the dashboard): a board or a monitor that cannot be read, a run that failed on Exa's side (for example `insufficient_credits`), a run that returned pages without a list of postings, a run still going after a later one has ended, and a run whose result cannot be read. The last one is tried again by the next two checks, with the runs after it waiting, and is then given up. These reach Telegram only in a message that has postings to send. A monitor paused or disabled on Exa's dashboard is reported by `monitor-sync` and not restarted. After more than thirty days without a check, `monitor` reads each monitor's latest 60 runs.

## News digest

`python hunt.py news` searches Exa's news category for each `[news].topics` entry in `profile.toml` (articles published in the last `--days`, default 7; 8 results per topic) and drops articles already considered (`news_state.json`, kept 90 days). With `TYPESAFE_API_KEY` set, Jev then answers a relevance yes/no for each new article (one request per article, given your target roles and topics): an article below 0.3 (`news.RELEVANT_MIN`) is dropped and printed, and only the rest reach Claude. Claude picks at most 8 worth your time (developments in the job market for your target roles, and substantive news in your topics), with a one-sentence takeaway each and a short overview, and the digest goes to Telegram with the links. Jev and Claude get your target roles, the topics and the article titles and excerpts, not your CV. Dropped articles are recorded in `news_state.json` too, so they are not screened again. Cost: about $0.007 per Exa search (one per topic), a fraction of a cent for Jev, plus one Claude call, a few cents; no Claude call when nothing new is relevant. `--dry-run` prints the digest without sending it or updating the state. A topic whose search fails is listed at the end of the message, and the command exits 1. If a Jev request fails, that article and the rest go to Claude. Run it weekly, for example with `0 8 * * 1 news` in `HUNT_SCHEDULE` (see [Deploy to Railway](../dashboard/README.md#deploy-to-railway)) or cron.

The chat bot makes the same digest when you ask it for news in Telegram: on these topics, sharing `news_state.json`, so that neither it nor `news` repeats the articles of a digest already sent, or on a topic you name in the chat, as a one-off that leaves the state alone. See [News in the chat](../inbox/README.md#news-in-the-chat).

Both stop before any paid call when `[news].topics` is not a list of strings (a bare string would be searched letter by letter) or when `news_state.json` does not map article URLs to times: `news` ends with the reason, and the bot tells you in the chat.

## Application kit

`python hunt.py apply-kit <domain>` drafts what you need to apply to a company's best role: an answer to each written question of the posting's application form, a short note to the hiring team and the points of your CV to put first. It is one Claude call, made only when you ask for it: no run, schedule or monitor writes a kit. On the dashboard it is **Write application kit…** in a company's details (see [Dashboard](../dashboard/README.md#dashboard)). Nothing is sent to the company: you read the text, correct it and paste it into the form yourself.

- **What it reads.** The company's newest saved result in `out/` whose fit names a best role with a posting link; a company that was never scored, or was scored without a posting (check careers, skip), stops the command with a message to run it first. Your profile and CV, as the scorer gets them. The company's saved research and the fit's reasons, concerns, scope and gap notes. And the posting's text, from the first place that has it: the saved run (the text it fetched for the scorer), the company's job board when it lists the posting with its text (free), Exa (about $0.001, only with `EXA_API_KEY` set). At most 8,000 characters are used. Without any text the kit is written from the role's title and says so under "Before you send".
- **The questions.** They are read from the posting's application form on its job board, and only Greenhouse and Ashby show a form's questions. Greenhouse lists them in its public job-board API. Ashby's come from the API its own hosted posting page loads the form from, which is not documented: if Ashby changes it, a kit has no questions until the code follows. A posting on another board has none, and one on the company's own site only when its link carries the board's id (`?gh_jid=`, `?ashby_jid=`). The kit then holds the note and the CV points. Only fields that ask for a written answer count, 12 at most: not the name, the CV upload, links (LinkedIn, GitHub, a website), phone, email, selects or checkboxes.
- **No invented facts.** Claude is told to use only what your profile and CV, the posting and the saved notes say, and never to invent an employer, a number, a tool or a result. Where an answer needs a fact the CV does not have it writes `[add: <what>]`, and a salary expectation is always `[add: ...]`. It names gaps honestly, from the fit's concerns and gap note, answers location and work-permit questions from your profile's `location` only, and writes in the posting's language. "Before you send" lists every `[add: ...]` and every claim to verify. These are instructions to a model, not a guarantee: read each answer against your CV before you send it.
- **Text from web pages.** The posting and the form's questions are a web page's text. Claude gets them as information about the job, with the rule never to follow them as instructions, has no tools in this call, and only the kit is read back. The dashboard shows the kit as plain text.
- **Cost.** One Claude call, a few cents (the saved file records the tokens), plus about $0.001 of Exa when the posting text has to be fetched. Reading the job board and its form is free.
- **Where it is saved.** `kits/<domain>.json` (git-ignored: it holds text drawn from your CV). One kit per company: a new one replaces the old. Next to the kit the file holds the questions found, where the posting text came from (`posting_source`: `saved`, `board`, `fetched` or `none`), the role's title and link, the saved run the role came from, the model and the token counts.
